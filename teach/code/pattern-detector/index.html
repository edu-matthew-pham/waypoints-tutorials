Teacher guide: Pattern Detector projects

Build an app that sorts an input (text, answers, a photo, a pose or a sound) into groups and responds usefully. One short lesson trains a model in the Pattern Trainer and runs it in Python; then three open projects: A uses rules you write, B a model you train, C joins the two. The apps run on your own computer, from the Pattern Detector starters.

Open the student course · How the ideas build

Each lesson works two ways. Students can work through the online tutorial at their own pace (it checks their answers and saves their progress in their browser), or you can teach it to the whole class from the slides, then send students into the tutorial for the Modify and Make steps.

Every lesson guide has plain-language notes, the answers to every check, a solution for every task, and slides and a worksheet for Waypoints Prepare. These guide pages are not linked from student pages, but they are not secret either: keep printed Teacher editions for answers you do not want students to find.

Course resources: Open course presentation in Prepare · Opening and closing slides (Markdown)

Course teaching guidance

These projects are written to be adopted or adapted. Nothing here belongs to one school's programme, task sheet or marking scheme: use the parts you want and change the rest.

What a pattern detector is. An app that takes an input (text someone types, answers to a few questions, a photo, a pose, a sound), sorts it into groups, and responds in a way that helps a real person. There are two ways to build the sorting part: rules you write (project A) or a model you train from examples (project B). Project C lets a trained model feed your rules. Students meet the trade-off first-hand: rules are easy to explain and fix but cannot cover every case; a trained model copes with messy inputs but can be sure and wrong, and cannot say why.

Where it sits, and the first lesson. After Apps with Gradio, beside Machine learning with Gradio (either first): this is the easier way into machine learning, because the Pattern Trainer does the training and the starters hide the numbers, so students need only Gradio apps, functions, if/elif and dictionaries. Machine learning with Gradio shows how a model works inside. The one lesson, Train a model, then use it in Python (about 40 minutes): a tiny two-class model trained in the Pattern Trainer, tested on the site's board, then the same my_model.json run in the Python starter. Install the starters before it (below). Brief A can come before or after it; B and C build on it.

How the apps run. The apps are Python with Gradio and run on the student's own laptop, starting from the Pattern Detector starters. Setup is once per laptop (a virtual environment and pip install -r requirements.txt; about 0.5 GB). Try it on a school laptop before the lesson: project A's starters need only Gradio (and numpy for the colour and sound starters), so they are the quickest to test. No camera or microphone is needed for A; the photo and sound starters also accept uploaded files.

Adapting a project. Each project's guide below lists what to change. The pattern is the same for all of them:

  • The problem and the user. Students choose their own; if you want a shared context (a class, a club, a subject), say so in the brief you give them.
  • The starters. Keep the four on offer, offer fewer to narrow the choice, or add your own starter in the same style (a header comment, # ADAPT: lines, a short IDEAS list).
  • The checklist. The "Check your app" list is the success criteria. Reword it, add a line for your own priorities, or drop one.
  • The marking points. Each guide gives points to look for against each checklist line. Replace them with your own criteria; nothing on this site is a mark scheme.
  • The help. Hints are always on offer and anything a student opens appears on their Show your teacher card as "Help used". "Show one way" is part of the example solution, so if you would rather no student sees any of it, note that the guide shows the example in full and leave it on and read the Help used list when you mark, or turn it off (see below).
  • The hand-in. Set your own. Students can show the badge card on screen, and "Download my code" saves what they pasted into the page.

Using the badge. Badges and ticks live in the student's browser. Ask students to press Show your teacher and show you the card (milestones ticked, help used, their own words on the hardest part). It is a self-assessed record, not a marked result.

Strategies for getting unstuck: Say what it should do, Test a small piece, Read the error, Trace it. A student who is stuck can try one before asking for a hint. The optional course How you learn best introduces them, and a few lesson decks have a short teach, show or nudge slide for one. (Each lesson page links to the cards from its first hint.)

A. Rules-based pattern detector (a function with parameters, elif, a dictionary ({k: v}), return)

Build a Python app that sorts an input into groups using rules you write yourself, then responds in a way that helps someone.

Some problems can be described exactly: does the message contain this phrase? Is the soil drier than this? For those, rules are quick and predictable, and you can always say why the app answered as it did. When it is wrong, you can find the rule and fix it.

Before you start, write one sentence: who is it for, and what will it help them do?

What to hand in

  • Your app: the .py file and any data files (your dictionary or lists).
  • Your rules in plain English: a short list or a flowchart.
  • A testing record: input, expected result, what the app did, with boundary cases.
  • A reflection: what your rules can't handle, and who could be affected if your app got it wrong.

Check your app before you hand it in

  • Clear result, in words your user understands.
  • Honest: says when an input doesn't match any rule.
  • Useful response: advice, a next step or an explanation, not just a label.
  • Fits your user: at least one setting or option they can change.
  • Tested on edge cases, not just the ones you designed it for.

Milestones:

  • My problem, my user and my rules are written in plain English.
    1. Start with one sentence: who is it for, and what will it help them do?
    2. List your groups, then ask of each one: what can I check to tell it apart?
    3. Write each rule as a sentence first, such as "if the soil is drier than 30%, water it". Turning it into an if comes later.
    Students can earn this piece (reveal on): # Rules in plain English (written first, before any code):
    # 1. Nothing typed -> ask for a password.
    # 2. On the list of common passwords -> Weak, whatever its length.
    # 3. Shorter than the minimum length -> Weak, say how many more characters.
  • My app runs, built from the closest starter with its ADAPT lines changed.
    1. Run the starter exactly as it is first, so you know what working looks like.
    2. Change one ADAPT line at a time and run it again, so you know which change broke it.
    3. Put the numbers your rules use together at the top, so they are easy to find and change after testing.
    Students can earn this piece (reveal on): if len(password) < min_length:
    return "Weak", f"{len(password)} characters. Aim for at least {min_length} ({min_length - len(password)} more)."
  • I tested the edges and fixed what broke.
    1. Try an input exactly on the boundary of a rule, then one just either side of it.
    2. Try nothing at all, odd spellings, and something your rules were never meant for.
    3. Write what you expect before you run each test, so a surprise is easy to spot. A testing record can be as simple as what you typed, any settings, and the first word you expect back.
    Students can earn this piece (reveal on): ("abc1234", False, "Weak"), # 7 characters: one under the boundary
    ("abc12345", False, "Strong"), # exactly 8: on the boundary
  • I can say what my rules can't handle, and why a trained model might do better.
    1. Find one input where your app gives a poor answer, and ask how many rules it would take to get it right.
    2. Think about who is affected if the app is wrong, and whether they would know it was wrong.

What this project is. The rules-based half of a pair (project B trains a model instead; project C joins them). Students sort an input into groups with rules they write, respond usefully, and then test and reflect honestly. The learning is in the testing and the reflection as much as in the app: at the boundary of a rule, with an empty input, and with the case no rule covers.

Running it. Each student works on their own laptop from a starter (links on the project page). Do the one-off setup before the lesson, or as a first step, and run an unchanged starter on a school laptop beforehand. Project A needs no camera or microphone; the photo and sound starters also accept uploaded files.

What to change when you adapt it

  • Problem and user. Students choose, or you set a shared context (a class, a club, a subject area). Say which in the brief you hand out.
  • Starters on offer. Offer all four, fewer to narrow the choice, or add a starter of your own in the same style (a header comment, # ADAPT: lines, a short ideas list).
  • The skills list. "You'll use" lights up from pasted code and is only a prompt: the unchanged starters already light some of it, or all (the page tells students so), so it shows which skills are in play, not that a student wrote them. Read the code for that. Change uses: in projects.yml if you want other skills.
  • Check your app. This is the success criteria. Reword a line, add your own, or remove one. The page lists them in the goal; the marking points below follow the same order.
  • Hand-in. Set your own. The Show your teacher card lists milestones ticked, the skills found in pasted code, help used and the student's own words on the hardest part.
  • Help. Hints are on offer to everyone. "Show one way" opens after the milestones before it are ticked or every hint for it has been used. Both are listed as Help used on the card, so you can see it when you mark. Set reveal: false (or remove reveal:) to turn "Show one way" off.

Marking points to look for (replace with your own criteria):

  • Clear result. The output is a word or sentence the named user would understand, not a variable name or number.
  • Honest. Some input leads to "I don't know" or "none of my rules fits", and the app does not pick a group anyway. In the example, symbols-only input is not rated.
  • Useful response. Each result comes with a reason, advice or next step. In the example, "Weak" always says why and how many characters are missing.
  • Fits the user. There is a setting the user can change (strict mode in the example) and the student can say why it helps this user.
  • Tested. The record includes an empty input, input exactly on a boundary (the example tests 7 and 8 characters), input that is nearly right (capital letters, a stray space), and something the rules were not made for.
  • Reflection. Names a real input that fails, says why more rules would not fix it, and says who would be affected, not just "it might be wrong".

Usual mistakes, and a question to ask.

  • Rules that overlap. Two rules both fit and the first one wins by accident. Ask: "Which rule fires for this input, and is that the one you meant?" (A rule order that matters should be written down.)
  • Numbers buried in the code. Boundaries typed in several places drift apart. Ask: "If you change this cut-off after testing, how many lines do you edit?"
  • Testing only the easy cases. All tests pass because they were designed to. Ask: "What is the smallest change to this input that should flip the answer?"
  • A label with no reason. The app says "Weak" and nothing else. Ask: "What would the user do next?"
  • Boundary off by one (< where <= was meant). Ask: "What happens at exactly 8?"

Ways it could look. Students see two screenshots of finished apps that work quite differently (a study method picker, a working checker): output only, never code, so they show the standard without giving one answer to copy. Replace them with your own screenshots if you like (a PNG in content/code/pattern-detector/projects/, listed under benchmark:).

The example below is one complete rules app (a password checker with a strict-mode setting, a list of common passwords, an honest "not sure" and a small testing record). It is for you, to calibrate marking. Students who unlock "Show one way" see only a short piece of it for the milestone they are on. If a student chooses a password checker, expect to see something different from this one.

A filled-in testing record (the example password checker; yours will look different):

I typed Strict I expected The app said Notes
(nothing) off ask for a password Type a password first. ok
PASSWORD off Weak Weak: "the most guessed password" capitals still caught
abc1234 off Weak Weak: 7 characters, 1 more one under the boundary
abc12345 off Strong Strong exactly 8: on the boundary
abcdefgh off OK OK: only one kind of character ok
!!!!!!!! off Not sure Not sure: no rule fits honest, no guess
abc12345 on Weak Weak: 8 characters, 4 more strict mode moves the boundary
Passw0rd! off Weak (I guessed) Strong surprise: a common pattern, but my rules cannot see it. Goes in the reflection.

A sample reflection (strong): "My rules only check length, kinds of characters and a short list of common passwords, so 'Passw0rd!' is rated Strong even though guessers try it early. To catch it I would need to know every common pattern, such as swapping a letter for a number, and that list has no end. A model trained on many real leaked passwords could learn that pattern, though I could not say why it rated one weak. If my app is wrong, a student might trust a weak password. They would not know, because the app says Strong with confidence."

What a weaker reflection looks like: "My app could be improved by adding more rules." Ask: which input, and how many rules would that take?

One possible solution
# Rules in plain English (written first, before any code):
#   1. Nothing typed                    -> ask for a password.
#   2. On the list of common passwords  -> Weak, whatever its length.
#   3. Shorter than the minimum length  -> Weak, say how many more characters.
#   4. Long enough, letters and numbers -> Strong.
#   5. Long enough, only one kind       -> OK, suggest mixing.
#   6. None of these fit                -> say so, don't guess.

import gradio as gr

# The numbers the rules use, together at the top
MIN_LENGTH = 8
STRICT_LENGTH = 12
COMMON = {
    "password": "the most guessed password in the world",
    "123456": "a counting sequence",
    "qwerty": "the first letters on a keyboard",
    "letmein": "a phrase everyone tries",
}


def check(password, strict):
    password = (password or "").strip()
    min_length = STRICT_LENGTH if strict else MIN_LENGTH
    if not password:
        return "Type a password first.", ""
    if password.lower() in COMMON:
        return "Weak", f"That is {COMMON[password.lower()]}. Guessers try these first."
    if len(password) < min_length:
        return "Weak", f"{len(password)} characters. Aim for at least {min_length} ({min_length - len(password)} more)."
    has_letter = any(ch.isalpha() for ch in password)
    has_digit = any(ch.isdigit() for ch in password)
    if has_letter and has_digit:
        return "Strong", "Long enough, with letters and numbers."
    elif has_letter or has_digit:
        return "OK", "Long enough, but only one kind of character. Mix in letters and numbers."
    else:
        return "Not sure", "None of my rules fits a password with no letters or numbers, so I won't guess."


# Testing record: what I typed, strict mode, the first word I expect
TESTS = [
    ("", False, "Type"),
    ("PASSWORD", False, "Weak"),    # capitals, same rule
    ("abc1234", False, "Weak"),     # 7 characters: one under the boundary
    ("abc12345", False, "Strong"),  # exactly 8: on the boundary
    ("abcdefgh", False, "OK"),
    ("!!!!!!!!", False, "Not"),
    ("abc12345", True, "Weak"),     # strict mode moves the boundary to 12
]
for given, strict, expected in TESTS:
    result = check(given, strict)[0]
    print("ok  " if result.startswith(expected) else "FAIL", repr(given), "->", result)

gr.Interface(
    fn=check,
    inputs=[gr.Textbox(label="Password to check"), gr.Checkbox(label="Strict mode (12 or more characters)")],
    outputs=[gr.Textbox(label="Rating"), gr.Textbox(label="Why")],
).launch(show_error=True)
B. Trained pattern detector (a function with parameters, a dictionary ({k: v}), comparing (== != < >), return)

Build a Python app that recognises your own groups of pictures, body poses or sounds, using a model you train yourself, then responds in a way that helps someone.

Some things are easy for people to recognise but almost impossible to describe as rules. Every breed of dog, every angle and every kind of light would need its own rule. Instead you show the computer lots of examples of each group (a class), it finds its own patterns, and then it uses them on things it has never seen. Its confidence in an answer, a number from 0 to 1 (0.8 means 80% sure), is not the same as being right.

Before you start, write one sentence: who is it for, and what will it tell or do for them?

What to hand in

  • Your app: the .py file and your model file.
  • A testing record: input, what you expected, what the app said and how sure it was. Include at least five inputs it had not seen before, and at least two that are not in any of your classes.
  • A reflection: what fooled it, what you changed because of it (more examples, a new class, a different cut-off), one thing a simple rule would do better than your model and why, and who could be affected if your app got it wrong.

Check your app before you hand it in

  • Clear result, in words your user understands.
  • Honest about how sure it is: it says when it is not sure instead of guessing.
  • Useful response: advice, a next step or a score, not just a label.
  • Fits your user: at least one setting or option they can change.
  • Tested on things you did not train it on.

Good habits. Only record yourself, or people who have said yes. Check what is behind you before you record. Your pictures and sounds stay on your computer. The model file holds only your class names and trained numbers, but a saved project file also holds tiny copies of your photos (in Sounds mode, just sound scores), so do not share it if it shows people.

Milestones:

  • My problem, my user and my classes are planned, and I have collected 20 or more examples of each.
    1. Start with one sentence: who is it for, and what will it tell or do for them?
    2. Pick two to five classes that look (or sound) clearly different to you. Add a "nothing" class only if your app will often see none of the others. In Sounds mode the trainer hears kinds of sound (a dog, a knock, music, speech), not which word was said, so two spoken words sound the same to it: hover over an example to see what it heard.
    3. Collect examples in different places, at different times and from different angles, not twenty copies of one situation. The model learns whatever is the same in all of them, including the background.
    Students can earn this piece (reveal on): # Plan (written before training):
    # User: someone hard of hearing, at home.
    # Job: tell them about sounds they would want to know about.
    # Classes: Baby crying, Dog barking, Fire crackling, Nothing urgent
  • I trained it, checked it, and tried hard to fool it.
    1. Try new examples that were not used for training, and write down what you expect before you try each one.
    2. Try to fool it: a new place, a different person who has said yes, a different angle, something that is not any of your classes. Note how sure it was, not just what it said.
    3. Every time it gets one wrong, add examples like that one to the class it should have been, and train again. Write down what you changed.
    Students can earn this piece (reveal on): # I tried I expected It said How sure
    # a sneeze Nothing urgent Baby crying 0.61 (now "Not sure")
    # a rooster Nothing urgent Dog barking 0.998 (fooled, and sure)
    # a chainsaw, first model Nothing urgent Fire crackling 1.00 (fixed by adding chainsaws)
  • My app runs, built from the closest starter with my model file and my ADAPT lines changed.
    1. Run the starter exactly as it is first, with its sample model, so you know what working looks like.
    2. Put your model file in the same folder as the starter, replacing the sample one, and run it again. Your class names come from the file.
    3. Say something different for each class, and keep those messages together in one place so they are easy to change.
    Students can earn this piece (reveal on): ADVICE = {
    "Baby crying": "The baby is crying. Go and check on them.",
    "Dog barking": "The dog is barking. Someone may be at the door.",
    "Fire crackling": "Something is crackling like a fire. Check the kitchen and the heaters now.",
    "Nothing urgent": "Nothing to worry about.",
    }
  • I chose my cut-off from my testing, and I can name one thing a simple rule would do better.
    1. Look down your testing record: how sure was it when it was right, and how sure was it when it was shaky or wrong? Pick the cut-off from those numbers, not a guess.
    2. Remember that a model can be very sure and still wrong. A cut-off catches the shaky answers, not the confident mistakes.
    3. For the rule: is there a part of your problem you could say exactly, with a measurement or a list, that the model only guesses?
    Students can earn this piece (reveal on): if score < cutoff:
    # Not sure is passed on, not dropped: a missed alert costs more than a false one.
    return "Not sure", f"I heard something, maybe {label} ({score:.0%}). Have a look to be safe."
    return label, ADVICE[label]

What this project is. The trained half of a pair (project A uses rules; project C joins them). Students train a model from their own examples, build an app around it, and then test whether it can be trusted. The learning is in the testing and the reflection as much as in the app: new people, new places and things outside every class, and a cut-off picked from evidence rather than a guess.

Running it. Students train in the browser-based Pattern Trainer, download one small model file, and run a starter on their own laptop. Do the one-off setup before the lesson, or as a first step, and run an unchanged starter with its sample model on a school laptop beforehand.

Check before class (these vary by school; two minutes on one student-account laptop):

  • The trainer loads. Open the Pattern Trainer in the browser students will use, and check the school filter does not block it.
  • The camera or microphone is allowed. The picture and pose modes need the camera, and the sound mode needs the microphone (or students can upload sound files). Check the browser prompts and shows the permission.
  • The install works without help. If students cannot install packages on their laptops, run the setup yourself or use shared machines.

For your IT team. The Pattern Trainer is a static page: it runs in the student's browser with no backend, database or accounts. Its libraries (TensorFlow.js, MediaPipe) and model files are in the trainer's repository and served from the same site, and its own code makes no fetch, XMLHttpRequest, WebSocket or beacon calls and uses no browser storage (checked against waypoints-tools at commit 8c7ec47, 27 Oct 2026; the vendored libraries were not audited). The camera or microphone is requested through the normal browser prompt, only when a student picks that mode. The only file output is the model file, or a saved project, that the student chooses to download. The starters run on the student's laptop and need Python, pip access for one install, and the model files in their own repository. Your IT team will make its own call; the trainer's privacy page says the same in plain words. To see it yourself: load the trainer, switch off Wi-Fi, and train a model, or watch the Network tab in the browser's developer tools while you add examples.

What to change when you adapt it

  • Problem and user. Students choose, or you set a shared context (a class, a club, a subject area). Say which in the brief you hand out.
  • Modes on offer. Offer pictures, poses and sounds, or narrow it. Poses and sounds suit students who are not comfortable on camera, since poses use only 33 body points and sounds use no pictures. Steer voice-command ideas away from the Sounds mode: it keeps only YAMNet's scores for 521 kinds of sound, so spoken words all come out as "speech" and look alike to the trained part (a model on four words from Speech Commands scored about chance on new speakers, 28 Oct 2026). It is the same lesson as CreateAI, which measures movement, so two held-still positions look alike: what the fixed part can notice limits what any model can learn.
  • Public datasets. An optional extra, not the main route: students collect their own examples for their own user. A dataset helps a student with no camera or microphone, and "train on theirs, test on yours" shows how a model fits the world it was trained in. Two with clear licences: ESC-10 (environmental sounds, CC BY 3.0, the example's data) and Rock Paper Scissors (computer-generated hands, CC BY 4.0, project C's). Avoid datasets of people's faces and bodies.
  • Amount of data. "20 or more examples of each class" is a prompt. Raise it for stronger models, or lower it for a short unit.
  • The skills list. "You'll use" lights up from pasted code and is only a prompt: the unchanged starters already light some of it, or all (the page tells students so), so it shows which skills are in play, not that a student wrote them. Read the code for that. Change uses: in projects.yml if you want other skills.
  • Check your app. This is the success criteria. Reword a line, add your own, or remove one. The page lists them in the goal; the marking points below follow the same order.
  • Hand-in. Set your own. The Show your teacher card lists milestones ticked, the skills found in pasted code, help used and the student's own words on the hardest part.
  • Help. Hints are on offer to everyone. "Show one way" opens after the milestones before it are ticked or every hint for it has been used. Both are listed as Help used on the card. Set reveal: false (or remove reveal:) to turn "Show one way" off.

Safety and consent. Students record themselves or people who have said yes. Remind them to check what is behind them. Pictures and sounds stay on the student's computer; the model file has only class names and trained numbers; a saved project file in the trainer also holds tiny copies of photos, so it should not be shared if it shows people. Decide before the unit what students may keep and where.

Marking points to look for (replace with your own criteria):

  • Clear result. The output names the class and says what it means for the named user, not a bare label or number.
  • Honest about how sure it is. There is a cut-off, the app says "not sure" under it, and the student can say where the number came from. Look for a cut-off taken from the testing record, not a round number picked early. In the example, 0.85 sits above the four shaky wrong answers (0.61 to 0.79) and below all but one right answer.
  • Useful response. Each class leads to different advice or a next step. In the example, each alert says what to do, and "not sure" still tells the user to look, because a missed alert costs more than a false one.
  • Fits the user. There is a setting the user can change (the cut-off slider in the example) and the student can say why it helps this user.
  • Tested. The record has at least five unseen inputs and at least two not in any class, with what was expected written before the result, and what the student changed in response.
  • Reflection. Names a real input that fooled the model, says what was changed, makes a fair rule-versus-model point, and says who would be affected by a wrong answer.

Usual mistakes, and a question to ask.

  • Testing only the training examples. Everything scores 0.99. Ask: "Which of these did the model not see before?"
  • Examples that are all the same. Twenty near-identical photos or sounds. Ask: "What would change if you moved to a different room, or someone else did it?"
  • Trusting the confidence. A high score is taken to mean right. Ask: "Is there an input it was very sure about and wrong?"
  • A cut-off picked by guessing. Ask: "Which numbers in your testing record did you use to choose it?"
  • No "nothing" case. The app always picks a class, even for something else. Ask: "What does it say if the camera sees an empty room?"
  • Class that is really the background. All the "dog" photos are outdoors and all the "cat" photos indoors. Ask: "Would it still say cat in the garden?"
  • Classes the mode cannot tell apart. Spoken words in Sounds mode, or two still positions on a movement sensor. Ask: "What does the trainer say it heard for each one?"

# EXAMPLE (teachers): a home sound alert, built from audio_pattern_trainer.py.
# Its model (my_home_sounds_model.json) was trained in the Pattern Trainer's
# Sounds mode on clips from ESC-10 (CC BY 3.0, Karol Piczak). Yours will look different.
#
# Who it is for: someone who is hard of hearing, at home.
# What it does: listens to a short recording and says whether it heard a baby
# crying, a dog barking or a fire crackling, and what to do about it. Anything
# it is not sure about is passed on as "not sure", never dropped.
#
# Plan (written before training):
#   User:     someone hard of hearing, at home.
#   Job:      tell them about sounds they would want to know about.
#   Classes:  Baby crying, Dog barking, Fire crackling, Nothing urgent
#             (rain, waves, a clock: sounds that need no action)
#
# Cut-off, chosen from the testing record (see the teacher notes): the four
# shaky wrong answers scored 0.61 to 0.79, and all but one right answer scored
# 0.87 or more, so 0.85 catches the shaky ones for the cost of one right answer
# (0.76). Some wrong answers are still 0.95 or more sure, which no cut-off catches.

import os
import gradio as gr
from pattern_model import PatternModel

MODEL_FILE = os.path.join(os.path.dirname(os.path.abspath(__file__)), "my_home_sounds_model.json")
model = PatternModel.load(MODEL_FILE)

DEFAULT_CUTOFF = 0.85

# What to say for each class (the names come from the model file)
ADVICE = {
    "Baby crying": "The baby is crying. Go and check on them.",
    "Dog barking": "The dog is barking. Someone may be at the door.",
    "Fire crackling": "Something is crackling like a fire. Check the kitchen and the heaters now.",
    "Nothing urgent": "Nothing to worry about.",
}


def reply(label, score, cutoff):
    """Turn the model's answer into words for the user."""
    if label is None:
        return "Nothing heard", "That recording was empty. Try again."
    if score < cutoff:
        # Not sure is passed on, not dropped: a missed alert costs more than a false one.
        return "Not sure", f"I heard something, maybe {label} ({score:.0%}). Have a look to be safe."
    return label, ADVICE[label]


def listen(sound, cutoff):
    if sound is None:
        return "Record or upload a sound first.", ""
    label, score = model.top(sound)
    headline, advice = reply(label, score, cutoff)
    return headline, advice


# Made-up answers, to test the wording and the cut-off without a microphone
TESTS = [
    (None, 0.0, "Nothing heard"),
    ("Baby crying", 0.99, "Baby crying"),
    ("Dog barking", 0.84, "Not sure"),      # just under the cut-off
    ("Dog barking", 0.85, "Dog barking"),   # exactly on it
    ("Nothing urgent", 0.97, "Nothing urgent"),
]
for label, score, expected in TESTS:
    got = reply(label, score, DEFAULT_CUTOFF)[0]
    assert got == expected, (label, score, got)

gr.Interface(
    fn=listen,
    inputs=[
        gr.Audio(sources=["microphone", "upload"], type="numpy", label="Record a few seconds, or upload a sound:"),
        gr.Slider(0.5, 0.95, value=DEFAULT_CUTOFF, step=0.05, label="How sure should I be before I say what it is?"),
    ],
    outputs=[gr.Textbox(label="What I heard"), gr.Textbox(label="What to do")],
    title="Home sound alert",
    description="For someone who is hard of hearing: sounds at home you would want to know about.",
    flagging_mode="never",
).launch(show_error=True)

Build a Python app where a trained model recognises something, and rules you write decide what to do about it.

Each part does the job it is best at. The model handles the messy, real-world input, such as a photo, a pose or a sound. The rules handle the parts you can describe exactly: counting, scoring, looking things up, and deciding what to do when the model is not sure.

Before you start: you have built one rules-based app (project A) and one trained app (project B).

The parts fit together like this:

input → trained model → label + how sure → your rules → response

Your rules should use how sure the model is, not only its label. What does your app do when it is not sure?

Before you start, write one sentence: who is it for, and what will it tell or do for them?

What to hand in

  • Your app: the .py file, your model file and any data files.
  • A pipeline diagram, with the reason each part is a model or rules.
  • A testing record for each part on its own and for the whole app, including inputs where the model was unsure or wrong.
  • A reflection: which part caused the most problems, what you would change, and who could be affected if your app got it wrong.

Check your app before you hand it in

  • Clear result, in words your user understands.
  • Honest about how sure it is: low-confidence results are handled, not hidden.
  • Useful response that needs both parts: take either part away and the response gets worse.
  • Fits your user: settings or options they can change.
  • Tested as a whole, not just part by part.

Good habits. Only record yourself, or people who have said yes. Check what is behind you before you record. Your pictures and sounds stay on your computer.

What this project is. The joined-up half of the set. Project A used rules and project B used a trained model; here a model feeds rules. The learning is in the joins: what the rules do with the model's label and confidence, and what happens when the model is unsure or confidently wrong. A strong project cannot work with either part taken away.

Running it. Same as project B: students train in the browser-based Pattern Trainer, download a model file, and run a starter on their own laptop, adding rules of their own. Run an unchanged starter with its sample model on a school laptop beforehand. The "Check before class" and "For your IT team" notes in project B apply here too.

When to offer it. After students have built one app of each kind, since the pipeline diagram only makes sense when they have met both a rule and a trained model. If a class has done only A or only B, offer it as an extension.

What to change when you adapt it

  • Problem and user. Students choose, or you set a shared context. Say which in the brief you hand out.
  • The model part. Offer pictures, poses and sounds, or narrow it. Students may reuse the model they trained for project B.
  • The rules part. The starters give simple examples to build from (choice_rules.py, sound_rules.py, measure.py); students may also write their own from scratch.

Marking points to look for (replace with your own criteria):

  • Clear result. Words the named user would understand, not a label and a number.
  • Honest about how sure it is. Low confidence changes what the app does, and the user can tell. In the example, an unsure throw is not played and the app says so.
  • Useful response that needs both parts. Ask: "If I removed the model, what would the app do? If I removed the rules?" In the example, the model alone can only name a hand shape, and the rules alone have no throw to play.
  • Fits the user. A setting the user can change (rounds to win in the example), and the student can say why.
  • Tested as a whole. A record of runs of inputs through the whole app, not only one input at a time, with at least one unsure case and at least one wrong case, and what the student did about each.
  • Pipeline diagram. Shows both parts and the hand-off between them, and gives a reason for each part, not just labels.
  • Reflection. Names the part that caused the most trouble, a real input that broke a join, and who would be affected.

Usual mistakes, and a question to ask.

  • A model with a few rules stuck on the end. The rules only rename the label. Ask: "What does the rules part know that the model does not?"
  • Ignoring confidence. The app takes the label at face value. Ask: "What happens when the model is 60% sure?"
  • Testing the parts but not the joins. Each part passes on its own, but the app fails together. Ask: "What is the first input that makes them disagree?"
  • Trusting a confident wrong answer. A rule acts on every label as if it were true. Ask: "What does your app do if the model is sure and wrong?"
  • A pipeline diagram that is decoration. It shows boxes but gives no reasons. Ask: "Why is this part not the other kind?"
  • Forgetting what the app remembers. A score that never resets, or resets at the wrong time. Ask: "When does this go back to zero?"

Two models in a row: detect, then judge (a stretch idea, with a worked example). Several models make sense when each looks at something different or answers a separate question: two senses (a sound and a picture), separate questions (which sign and which hand: 4 + 2 classes, not 8 combinations), a gate before a specialist, or a closer look for the second step. Splitting one question about one photo into a chain rarely helps at this scale (both models read the same 1,280 numbers, and their mistakes multiply).

The worked example, combined-banana-checker.py, is the strongest case: a ready-made model and the student's own model, each doing what the other can't. MediaPipe's Object Detector (EfficientDet-Lite0, Apache 2.0; it ships with the same MediaPipe the trainer and starters use, and knows COCO's 80 everyday things, banana, apple and orange among them) finds each banana and its box; the app cuts each one out; a ripeness model trained in the Pattern Trainer on BananaID (single bananas on a plain background; Mutrofin, Fatichah, Yuniarti and Setiawan, Mendeley Data, CC BY 4.0) judges it; rules apply two cut-offs (is it a banana: 0.30; how sure of the ripeness: 0.60), count and advise. Students cannot train a detector (it took thousands of photos with boxes drawn on them), but they can train the part that is theirs. The point is knowing where it fails, not a perfect app.

# EXAMPLE (teachers): a combined app. A trained model reads your hand;
# rules play the game. Built from image_pattern_trainer.py, with a model
# (my_rps_model.json) trained in the Pattern Trainer on 60 pictures per class
# from the Rock Paper Scissors dataset (CC BY 4.0, Laurence Moroney; the hands
# are computer-generated). Yours will look different.
#
# Who it is for: anyone who wants a quick game against the computer.
# What it does: you show a throw to the camera, the computer picks one, and the
# rules say who won the round. First to 2 wins. A throw it can't read well
# enough is not played: you show it again.
#
# Pipeline:
#   photo -> MODEL (Rock/Paper/Scissors + how sure) -> RULES (cut-off, who wins, score) -> result
#   MODEL: telling a hand shape apart in a photo is too messy for rules.
#   RULES: who beats whom, keeping score and when the game ends are exact.
#
# Cut-off, chosen from the testing record (see the teacher notes): from 0.70 to
# 0.85 it catches the same 5 of the 10 wrong answers; 0.70 asks you to show it
# again least often (12 of 80 right answers). Asking again costs little in a
# game; losing a round you won does not. 5 wrong answers were 0.85 or more sure.

import os
import random
import gradio as gr
from pattern_model import PatternModel

MODEL_FILE = os.path.join(os.path.dirname(os.path.abspath(__file__)), "my_rps_model.json")
model = PatternModel.load(MODEL_FILE)

CUTOFF = 0.70          # under this, the throw is not played
DEFAULT_TARGET = 2     # rounds to win the game

BEATS = {"Rock": "Scissors", "Paper": "Rock", "Scissors": "Paper"}   # each beats the one it names
NEW_GAME = {"you": 0, "computer": 0}


def round_winner(you, computer):
    """RULES: who wins one round."""
    if you == computer:
        return "draw"
    if BEATS[you] == computer:
        return "you"
    return "computer"


def play(score, label, confidence, computer, target):
    """RULES: one throw. Returns the new score and what to say. An unsure throw is not played."""
    if label is None or confidence < CUTOFF:
        return score, "Show it again", f"I'm not sure that was {label} ({confidence:.0%}), so that throw doesn't count."
    score = dict(score)
    winner = round_winner(label, computer)
    if winner != "draw":
        score[winner] += 1
    said = f"I read your throw as {label} ({confidence:.0%}). I threw {computer}."
    if score["you"] >= target:
        return dict(NEW_GAME), "You win the game!", said + f" Final score {score['you']}-{score['computer']}. New game."
    if score["computer"] >= target:
        return dict(NEW_GAME), "I win the game!", said + f" Final score {score['you']}-{score['computer']}. New game."
    headline = {"you": "You win the round", "computer": "I win the round", "draw": "Draw"}[winner]
    return score, headline, said + f" You {score['you']}, me {score['computer']}."


def throw(image, score, target):
    if image is None:
        return "Show a throw first.", "", score
    label, confidence = model.top(image)          # the MODEL part
    computer = random.choice(list(BEATS))
    score, headline, detail = play(score, label, confidence, computer, int(target))   # the RULES part
    return headline, detail, score


# The rules tested on their own, with made-up readings and no camera.
# Each throw is (my label, how sure, the computer's throw).
def run(throws, target=DEFAULT_TARGET):
    score, said = dict(NEW_GAME), None
    for label, confidence, computer in throws:
        score, said, _ = play(score, label, confidence, computer, target)
    return score, said

assert run([("Rock", 0.95, "Scissors")]) == ({"you": 1, "computer": 0}, "You win the round")
assert run([("Rock", 0.95, "Paper")]) == ({"you": 0, "computer": 1}, "I win the round")
assert run([("Rock", 0.95, "Rock")]) == (NEW_GAME, "Draw")
assert run([("Paper", 0.65, "Rock")]) == (NEW_GAME, "Show it again")              # unsure: not played
assert run([("Paper", 0.70, "Rock")]) == ({"you": 1, "computer": 0}, "You win the round")   # on the cut-off
assert run([("Rock", 0.9, "Scissors")] * 2) == (NEW_GAME, "You win the game!")    # first to 2, then a new game
assert run([("Rock", 0.9, "Scissors")] * 2, target=3) == ({"you": 2, "computer": 0}, "You win the round")

gr.Interface(
    fn=throw,
    inputs=[
        gr.Image(type="pil", sources=["webcam", "upload"], label="Show your throw:",
                 image_mode="RGBA", webcam_options=gr.WebcamOptions(mirror=False)),
        gr.State(dict(NEW_GAME)),
        gr.Slider(1, 5, value=DEFAULT_TARGET, step=1, label="Rounds to win the game:"),
    ],
    outputs=[gr.Textbox(label="Result"), gr.Textbox(label="What happened"), gr.State()],
    title="Rock paper scissors",
    description="Show rock, paper or scissors. First to win the rounds wins the game.",
    flagging_mode="never",
).launch(show_error=True)
