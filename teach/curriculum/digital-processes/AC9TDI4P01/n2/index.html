User story structure

AC9TDI4P01 n2 · waypoint 2 of 3 · Years 3–4 Digital Technologies (processes) · Processes and production skills · Hinge

Draft, from Waypoints Kit v0.2. Generated from Kit's node data and not yet reviewed by a specialist in Digital Technologies (processes): treat it as a starting suggestion and check it before use.

Checkpoint

Students can write a user story using a template that identifies who the user is, what they need, and why

Success criteria

  • Completes all three parts of a user story template
  • User is a specific person or group, not a generic description ('everyone')

Prior knowledge

Waypoint 1: What design criteria are.

Width

Minimum
Complete a user story template ('A [user] wants [need] so that [reason]') for a familiar, simple problem
Typical
Co-create user stories for a range of simple problem contexts; identify the user, need and purpose for each; refine a user story when the 'so that' reason is missing or unclear
Wider
  • Write user stories from the perspective of users in different circumstances — for example, a First Nations student in a remote community who wants to explore neighbouring countries to compare how people live; discuss how context shapes the user story
  • Investigate user stories for problems involving non-human users (e.g. a ranger group monitoring turtle populations) — discuss whether user stories still work and what changes

Hinge

A malformed user story (missing user, need or purpose) leaves nothing to check criteria against in N3 — the integration collapses if the user story is a stub.

Response modes

Where extra effort goes at this waypoint (width), not what kind of lesson it is.

Context breadth: more contexts in the vary or modify stepStudents who write user stories for only familiar contexts (their own problems) often struggle to write from an unfamiliar user's perspective. Practice across diverse user contexts builds the habit of identifying with users rather than projecting own needs.
