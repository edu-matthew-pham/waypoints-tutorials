Verifying and fixing programs

AC9TDI6P05 n3 · waypoint 3 of 3 · Years 5–6 Digital Technologies (processes) · Processes and production skills

Draft, from Waypoints Kit v0.2. Generated from Kit's node data and not yet reviewed by a specialist in Digital Technologies (processes): treat it as a starting suggestion and check it before use.

Checkpoint

Students can state expected program behaviour, test it by running the program, and fix errors when actual behaviour differs from expected

Success criteria

  • States the expected output before running the program
  • Identifies at least one discrepancy between expected and actual output and locates it in the code

Prior knowledge

Waypoint 2: Branching and iteration in programs.

Width

Minimum
State what the program should do for a specific input, run the program with that input, and identify whether the actual output matches — fix at least one error
Typical
Test the program with multiple inputs including edge cases (e.g. exactly at a boundary condition); describe each error found, locate it in the code, and fix it; re-test after fixing
Wider
  • Use systematic testing — a table of inputs and expected/actual outputs — to verify a program, including inputs that should trigger each branch and boundary values for loops
  • Diagnose and fix a provided program with a deliberate error — e.g. a direction is reversed, a condition is wrong — by reading the code before running it to predict the bug

Response modes

Where extra effort goes at this waypoint (width), not what kind of lesson it is.

Structured reasoning: a worked chain of reasons, then a write-and-compare (reasoning) checkStudents typically run programs to find bugs rather than reasoning about what should happen first. Establishing the expected-then-actual routine (state expectation → run → compare → locate error) makes debugging a reasoning activity rather than a trial-and-error one.
