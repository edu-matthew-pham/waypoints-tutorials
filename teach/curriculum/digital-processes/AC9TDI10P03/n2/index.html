Designing a relational database schema

AC9TDI10P03 n2 · waypoint 2 of 4 · Years 9–10 Digital Technologies (processes) · Processes and production skills · Hinge

Draft, from Waypoints Kit v0.2. Generated from Kit's node data and not yet reviewed by a specialist in Digital Technologies (processes): treat it as a starting suggestion and check it before use.

Checkpoint

Students can design a relational database schema with multiple tables, primary keys and foreign keys that captures the entities and relationships in their model.

Lessons on this site

No lesson is tagged to this waypoint. The standard is generally covered by some courses; see the standard's page for which are the main focus and which only touch it.

Success criteria

  • Schema has at least two tables each with a primary key
  • A foreign key correctly links the tables and reflects the modelled relationship
  • Data types are appropriate for each attribute

Prior knowledge

Waypoint 1: Modelling entities and their attributes.

Width

Minimum
Design at least two database tables with a primary key in each and a foreign key linking them; explain what the foreign key relationship represents.
Typical
Design a relational schema for a multi-entity domain; define primary keys, foreign keys and appropriate data types for each attribute; explain how the schema enforces the relationships between entities.
Wider
  • Design a schema that resolves a many-to-many relationship using a junction table — explain why this is necessary and how the junction table works
  • Evaluate an existing schema for redundancy and normalisation issues — identify what problems the original design causes and how to resolve them

Hinge

Schema design errors (wrong primary/foreign keys, wrong data types, missing relationships) propagate directly into N3 — a student cannot build a correct database from an incorrect schema, and subsequent queries will fail or return wrong results.

Response modes

Where extra effort goes at this waypoint (width), not what kind of lesson it is.

Structured reasoning: a worked chain of reasons, then a write-and-compare (reasoning) checkSchema design requires students to reason from the entity model to implementation decisions: which entity owns the foreign key? What data type suits each attribute? How do we represent a many-to-many relationship? Without a reasoning scaffold, students produce schemas by intuition and make structural errors that are hard to debug.
