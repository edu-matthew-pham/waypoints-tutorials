Defining the problem with precision and scope

AC9TDI10P04 n3 · waypoint 3 of 4 · Years 9–10 Digital Technologies (processes) · Processes and production skills · Hinge

Draft, from Waypoints Kit v0.2. Generated from Kit's node data and not yet reviewed by a specialist in Digital Technologies (processes): treat it as a starting suggestion and check it before use.

Checkpoint

Students can write a precise problem definition that names the problem, identifies scope boundaries, and acknowledges what is and isn't solvable within the project.

Success criteria

  • Problem definition names the specific problem (not just a domain)
  • Identifies at least one scope boundary (what is out of scope)
  • Problem definition is connected to the user stories rather than developed independently

Prior knowledge

Waypoint 2: Creating user stories.

Width

Minimum
Write a problem definition statement that names the problem clearly and identifies at least one scope constraint (what is and isn't being solved).
Typical
Write a problem definition with precision about what the problem is, what it is not, and whether it is solvable in the available timeframe; connect the definition to the user stories; identify questions that need answering before design can begin.
Wider
  • Explore how a broadly framed problem ('How do we encourage people to balance energy intake?') can be decomposed into sub-problems — identify which sub-problems are solvable with a digital system and which are not
  • Examine how recognising diverse stakeholder perspectives changes the problem definition — what looks like one problem from one stakeholder's view is a different problem from another's

Hinge

A problem definition without scope boundaries makes N4 criteria impossible to evaluate — students cannot check whether criteria are met if the problem itself is not precisely defined.

Response modes

Where extra effort goes at this waypoint (width), not what kind of lesson it is.

Structured reasoning: a worked chain of reasons, then a write-and-compare (reasoning) checkStudents tend to leap from a problem statement to a solution before the problem is well-defined. A reasoning scaffold — what exactly is the problem? → for whom? → what would count as solving it? → what is out of scope? — prevents premature solution framing and produces more useful design criteria.
