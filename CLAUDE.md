# Working notes for Claude (read first)

Waypoints tutorials: a static site (GitHub Pages) of markdown lessons with recorded clips and live playgrounds. Owner: Matthew (teacher, CGGS). He prefers direct, concise, high-signal replies.

## How we work
- "Let's track and discuss" means: record proposals in `ROADMAP.md`, commit locally, do not push, do not build.
- "go" (or "defaults") means: build the whole batch, test in a headless browser, commit with the attribution trailers, `git push origin HEAD:main`. Do not re-render clips locally (CI records them); render one lesson (`node tools/render.mjs --lesson <slug>`) only to look at a new or changed clip. Batch the work into one push where possible.
- Pushing triggers a Pages deploy (a newer push cancels a running one), so do not push while a run should finish. Commits that only change root `*.md` docs do not deploy.
- Clip reuse: a clip's hash covers its lesson folder (not `lesson.md`), `tools/render.mjs`, `tools/stage.html` and the one playground its app serves plus `playground-shared` and that playground's snippets file. CI downloads every clip and cheat-sheet picture whose hash matches the live site (`--seed <site>` on `render.mjs` and `render-pictures.mjs`) and records or draws only the rest; when nothing is new it skips installing Chromium, ffmpeg and lesson apps, so the deploy takes about a minute. Editing `render-pictures.mjs` redraws every picture (about 1.5 minutes). Editing `render.mjs` or `stage.html` re-records every clip (about 8 minutes).
- Do not add rigid pedagogy rules. Clips only where useful (hook, expected result without code, explaining why).

## Teaching decisions
- PRIMM: Predict (lock in, compare after Run), Run, Investigate, Modify, Make. Investigate tools must follow the lesson insight. Several tasks per step show as sub-pills only when more than one.
- Show combinations (a link in a list item, a list in a list, a picture in a link) and make the clip, the Explain it to me text and `explainPicture` cover the same ground (BUILDING › 4). `picture:` shows what code makes (rendered by the playground, Boxes optional).
- Expected results are clear and shown (BUILDING › 4): a picture (`expected:`, HTML) when static, an output-only clip when it moves, a short captioned clip to explain a spatial idea; never the code.
- Real-world content is a small complete example students Modify (the heading names the task). Make is an explicit task. Large projects belong to the teacher (For teachers panel).
- Foundations first, spiral curriculum, mastery shown by repeated use. Order: 1 intro, 2 variables, 3 decisions, 4 lists, 5 functions, 6 parameters, 7 returns, 8 modules, 9 events, 10 build a button, then the final challenge: 11 Catch the turtle, 12 Power-ups (these two mark "Challenge complete"), 13 Control panel (optional, UI direction), 14 Game levels (optional, games direction). Low floor, high ceiling: milestones with fading support, creative options in For teachers.
- Units group lessons (the word "module" is avoided: it means a Python module). A course's `index.md` lists `units:` (id, title, summary) and may name a `challenge:` unit; a lesson has `unit:` and may be `optional: true` (not needed for completion). `code/index.md` lists `pathways:` (Python, Web, MakeCode) with courses by `path` (built) or `title` + `summary` ("Coming later"), each `stage: foundations | extensions`.
- Progress is per-browser localStorage only; no class tracking.
- Pathways (see ROADMAP "Pathways"): options, not year gates. Foundations now: MakeCode (micro:bit then robots, or Arcade; blocks to Python), Python Foundations with Turtle (then checkpoint), HTML & CSS basics. Extensions later: console bridge, Gradio → ML, microStudio, p5.js → DOM. Typical fit (Years 6–8 vs 9+) is a teacher note only. Pygame parked.

## Playground runtime
- HTML playground: live preview (no Run); **Boxes** button or `?boxes=1` outlines every element with its tag name, coloured by depth (skips the browser-added `tbody`; rows get a thick outline, no label); `?zoom=` enlarges code and preview for clips. **Box model** button, `?boxmodel=1` or `?inspect=<selector>` (pinned): a layout-neutral overlay of margin, border, padding and content with sizes, for the CSS lessons (Boxes and Box model are never on together). `picture:` takes `inspect:` too. Pictures render in standards mode, like the preview. Every preview gets a `<base>` pointing at `_playground-html/media/` (course pictures from `media/html/`, so `src="trophy.svg"` works) and a click handler: web links open in a new tab, `#name` links scroll. Injected parts go before the student's code (after a `<!DOCTYPE>`). Sending a form shows a note ("Nothing was sent..."): the preview is sandboxed without forms, on purpose.
- `npm run check-html` walks every HTML lesson: regions render, pictures load, every check passes with its stored answer, every solution ticks its code check.
- The turtle playground is our own Skulpt bridge (`playground/skulpt-bridge.js`) plus a canvas renderer (`playground/canvas-turtle.js`), not Skulpt's turtle.
- Events: `onscreenclick`, `onkey`, `ontimer`, `listen`, `textinput`, `numinput`. `mainloop()`/`done()` waits for events until Stop; with nothing registered it returns at once. Code checks and the Run-step compare box accept a Stopped run. Keys need the picture clicked first.
- `predict` check: a locked prediction is stored in `wp-predict`; the next Run step shows it beside the real result.
- MakeCode playground (`playground-makecode/`, `try: { playground: microbit | arcade }`): the real MakeCode editor in controller mode; our page stores the projects (per step, `wp-makecode-playground:<step>`) and reports `main.ts` (blocks compile to it) on the HTML playground's channel, quiet until the student changes something. Each step's editor loads on click ("Open the MakeCode editor"; Full screen and `?full=` open it too), because MakeCode focuses itself on load and lazy-loaded editors scrolled the page. Follow the protocol rules in ROADMAP › MakeCode: embedding check (answer every re-sync with all projects, follow the new id after import, name in `pxt.json`). Code rules: `contains`, `inside: { "basic.forever": [...] }`, `count`, and `defs`/`calls`/`params` reading named MakeCode functions; students see the check text, not the rules. `language: makecode` lessons show code as blocks pictures (drawn by `render-pictures` through `render.html`, else live from MakeCode's renderer). What a program makes is drawn by MakeCode's own simulator at build time: `render-pictures` (section makecode-out) loads each `explainPicture` and `picture:` program into the playground in picture mode (`?sim=1`), starts the simulator and screenshots its biggest canvas or svg into `_pictures/makecode-out/<slug>/<key>.png`; the page shows it beside the blocks ("What it makes"). Test against the mock with `MAKECODE_EDITOR=/_mock/index.html` (a mock editor and simulator copied into `dist/_mock/`). This sandbox cannot reach makecode.com: test with the mock editor served at its address (Playwright route). MakeCode lessons can name extensions in frontmatter (`extensions: [robot]`, keys and pinned versions in `MAKECODE_EXTENSIONS`): the lesson page passes them as `?pkg=name=version,...` to each playground (added to the project's `pxt.json` dependencies) and as `options.package` to the blocks renderer (page and build time).

## Layout
- `content/<path>/<lesson>/lesson.md` plus code files with `# region: name` blocks. Frontmatter: title, summary, order, hook, unit, optional, author, language, modules, app, pacing.
- `tools/lesson-core.mjs` (pure parse/validate, `evalRules`, `parseTrace`) and `tools/lesson-view.mjs` (page HTML/CSS/JS) are shared with the create page. `tools/build-site.mjs`, `tools/render.mjs` (Playwright + ffmpeg clips), `tools/validate.mjs`.
- `playground/` (turtle), `playground-html/`, `playground-shared/snippets.js`, `snippets/*.json`, `modules/` (shared Python modules), `site/progress.js`, `create/`.
- Docs: `BUILDING.md` (how to design, build and test a course: read before starting a new course or unit), `AUTHORING.md` (lesson format and check types), `README.md`, `ROADMAP.md` (done and proposed).
- Check types: reflect, question (optional per-option `feedback`), code, number, bug, match, trace, parsons, predict, sort (items into groups; groups can repeat), answer and board (maths and science). Code rules: defs, calls, loops, returns, params, imports, uses, and `contains` (code fragments that must appear, spaces ignored); the HTML playground takes only `tags` and `contains`, and reports its code on every preview update (no Run), first report `quiet`. Error items also take `fault:` and `misconception:` (ids in `misconceptions.json`); validate warns on off-path errors (AUTHORING.md, Error tasks).
- Snippet ids are slugs of labels (for example `if-else`); lessons unlock them with `unlocks:`. Students see snippets as the **Reference** drawer over the canvas/preview: cards with Copy buttons (no click-to-insert), search, and a This lesson / All filter (This lesson = the lesson's unlocks via `slug` in `unlocks.json`, snippets the starter code uses via first-line patterns or a snippet's `matches`, lesson modules, My tools). Cards with an `example` get an **Example** button (that card only: the example program with Copy, and its picture). Run closes it; in the HTML playground a paste closes it. The full Reference page (`<course>/reference/`) shows each example and picture, and links to student cheat sheets at `reference/print/` (whole course and per unit; no links into `/teach/`). Each "Try it yourself" has a Full screen / inline toggle (a CSS class, so the iframe keeps its state; Esc returns).
- Caching: `build-playground` stamps playground JS/CSS URLs and the lesson iframes with `?v=<hash>` (`version.txt`); data JSON is fetched with `cache: 'no-cache'`. GitHub Pages caches for about 10 minutes, so unstamped files would show old behaviour after a deploy. My tools can be copied, edited and removed; student modules are global per browser (`wp-mymodules:turtle`); lesson modules offer "Open a copy to edit" once `my-module` is unlocked.
- Site navbar on every page (`siteNav`, `NAV_CSS`, `NAV_JS` in `lesson-view.mjs`; `navFor`, `SUBJECTS` in `build-site.mjs`): **Learning Waypoints ↗** (learningwaypoints.com, `MAIN_SITE`), **Tutorials** (this site's home), then one menu per subject (a top-level content folder; today only **Code ▾**) listing its pathways from `pathways:` in its `index.md` (Python, Web, MakeCode); the pathway of the current course or pathway page is marked. Courses are not in the navbar. Pathway pages are generated at `<subject>/paths/<id>/` (summary, optional `about:` Markdown, foundations and extensions cards with progress, "Coming later" placeholders, and a "nothing to open yet" note when no course is built, as for MakeCode). Course URLs stay where they are (progress is keyed by lesson slug). New subjects (Maths, Science) appear as menus only once they have content. On phones everything folds into Menu ▾. Then for the current course Playground, Reference and My progress (the course page; there is no progress dialog any more). Sticky: `NAV_JS` sets `--nav` to its height (it wraps to more rows on phones), and the lesson course bar, the step pills, `scroll-margin` and `scroll-padding-top` all offset by it. Lesson pages remember the last step the student worked in (clicked, typed, used its playground) per tab in sessionStorage `wp-from`; other pages show "← Back to <lesson> › <step>", or "Continue:" from `wp-last-lesson` on the playground and reference in a new tab.
- Runtime limits that shaped the challenge: one turtle only (no decoys); the turtle sprite's colour is fixed (a gold `dot` marks a gold turtle); clicks wait until an animated move ends, so moving targets step on a 50 ms timer with `speed(0)`.
- Course pages (a folder of lessons, such as `/code/python/`) lead with progress: a Continue card (the last-opened unfinished lesson, else the first unfinished, linking to the next unfinished step), lessons grouped into units ("n of m done" per unit), one collapsed row per lesson (number, title, Optional tag, a segment per check, status) that opens to its step list and a Start / Continue button; the Continue card's lesson opens by default; a "Challenge complete" badge when the challenge unit's required lessons are done, Done / n of m / Not started, Playground and Reference as chips, and a footer (snippets unlocked, next unlock, My tools, My modules). Filled client-side by `site/progress.js` from `wp-progress`.
- Teacher layer: `teacher.yml` beside each `lesson.md` (plain-language notes, goals, stuck list, exit ticket, student `explain`, `solutions` map to `sol-*` regions that must pass their code check); unit primers in `content/<course>/primers/<unit>.md`. `tools/teach.mjs` generates `/teach/<course>/` (course guide with primers and cheat sheets) and `/teach/<course>/<lesson>/` (guide, `deck.md` Prepare Marp, `worksheet.md` Prepare Print), linked only from the course footer. Cheat sheets: printable A4 pages per unit and for the whole course (`cheatsheet-<unit>/`, `cheatsheet/`) plus Markdown for Prepare; a unit lists what its lessons unlock or use (`unitSnippets`, patterns from `tools/snippet-pattern.mjs`); pictures come from a snippet's `example`/`shows`, drawn by `tools/render-pictures.mjs` (part of `npm run render`, cached in `dist/_pictures/`; HTML examples are rendered as pages into `dist/_pictures/html/`, and a picture's `div` sets its printed scale). No QR codes (no phones in class). Lesson URLs take `?full=step-N` to open that playground full screen. Prepare's load-by-URL parameter is unconfirmed, so pages offer "Copy address for Prepare". Maths and science board steps put the live board on the slide with `{{embed: URL}}` (Prepare loads it on the active slide only, allows only this site's origin, and shows a link in PPTX export and the student deck). Deck slides are sized by an estimate in `fitCode`; run `npm run check-decks` (marp-cli + Chromium overflow check) after changing deck layout.
- Region markers: `# region:`, `// region:`, `<!-- region: -->` and `/* region: */` (CSS).
- Multi-file examples: `# file: name.py` lines split code into panels; bug answers then use `"name.py:7"`.

## Commands
- `npm run validate`, `npm run render` (clips), `npm run build` (site), `npm run all`. A full `all` takes about 2 minutes.
- Local browser tests: Chromium at `/opt/pw-browsers/chromium` with `--no-sandbox`, serve `dist/` with a small static http server. Scratch scripts go in `.render-tmp/` (gitignored; `render` deletes it, so `mkdir -p .render-tmp` first).
- The turtle playground animates; in tests set speed to 10 and click Finish, or wait for the status to leave "Running".

## Gotchas
- Quote YAML captions that contain colons.
- HTML lessons: tags in Markdown text (lesson text, task bodies, hints, teacher Markdown fields) go in backticks (a bare `<h1>` becomes a real tag on the page, guide and slides; a bare `<style>` swallows the page's script); validate warns, and `check-html` fails if a lesson script did not run. Plain-text check and teacher fields are escaped by the generators (`pt` in `teach.mjs`).
- Display-only code regions (bug, compare, parsons) are not meant to run.
- Commit trailers: the `Co-Authored-By:` and `Claude-Session:` lines from the session reminder (they name the current model and session).
- Custom domain tutorials.learningwaypoints.com: DNS and the Pages setting are on Matthew's side.
