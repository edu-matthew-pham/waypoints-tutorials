## How we work
- "Let's track and discuss" means: record proposals in your subject's roadmap file (`roadmap/code.md`, `maths.md`, `science.md`, or `shared.md` for the build and shared tools), commit locally, do not push, do not build.
- Parallel chats (one each for code, maths and science): follow ROADMAP.md › Working in parallel. Pull before starting and before every push, keep notes in your own roadmap file, check `roadmap/shared.md` and `git log` before changing a shared tool, never force-push.
- "go" (or "defaults") means: build the whole batch, test in a headless browser, commit with the attribution trailers, `git push origin HEAD:main`. Do not re-render clips locally (the publish workflow records them); render one lesson (`node tools/render.mjs --lesson <slug>`) only to look at a new or changed clip. Batch the work into one push where possible.
- Pushing deploys nothing: the site changes only when Matthew runs the manual publish workflow (Temporary home, above). Say what is ready to publish when a push is done.
- Clip reuse: a clip's hash covers its lesson folder (not `lesson.md`), `tools/render.mjs`, `tools/stage.html` and the one playground its app serves plus `playground-shared` and that playground's snippets file. CI downloads every clip and cheat-sheet picture whose hash matches the live site (`--seed <site>` on `render.mjs` and `render-pictures.mjs`) and records or draws only the rest; when nothing is new it skips installing Chromium, ffmpeg and lesson apps, so the deploy takes about a minute. A picture's hash covers its own section of `render-pictures.mjs` (draw function, viewport, the helpers named in its `base`), so editing one section redraws only that kind; changing `pictures()`, `open()` or the browser setup needs a `SHARED` bump and redraws all 558 (350 are MakeCode blocks; tens of minutes, not seconds). The build job stops at 40 minutes. Editing `render.mjs` or `stage.html` re-records every clip (about 8 minutes; longer the first time spoken lines are made in three voices).
- Voiceover (`voice:` in a lesson's frontmatter, AUTHORING › Voiceover): Kokoro in Node at render time, captions stay first and clips stay muted by default. A choice of voices (12 Oct): every voiced clip is spoken in Emma, George and Heart; the lesson's voice is in the `.mp4`, the others are `clips/<id>.<voice>.m4a` played in step by `VOICE_JS` (`lesson-view.mjs`), picked per browser (`wp-voice`); captions and the first click after them are timed by the slowest voice. `render.mjs` builds clips from screencast frames placed at their drawn time (no Playwright `recordVideo`), so busy boards stay in step with the voice. This sandbox cannot reach Hugging Face: test timing with `WP_VOICE_ENGINE=flite` (robotic; never published: each voiced clip's `<id>.json` records its `voice`, `build-site` refuses flite clips, and a Kokoro build re-records any clip whose voice is not kokoro) and hear the real voice after a manual publish (the Voiceover preview workflow is parked in `.github/workflows-off/`). A voiced clip's hash also covers `tools/voice.mjs` and `tools/voice-lexicon.json`.
- Explain clips: HTML and Python lessons type code live; Python challenge lessons run the solution output-only (`view: output`, never showing solution code) and press buttons with `click: { selector: "#canvas", at: [x, y] }` (turtle coordinates); MakeCode lessons record the explain stage (`_playground-explain/`: blocks picture, then What it makes; AUTHORING › MakeCode explain clips).
- Effort (11 Oct): students expect coding to be fun and easy, so lessons cut friction and name the hard part (AUTHORING › Effort and struggle). New lessons get `struggle:` in `teacher.yml`, goals a student would recognise (they end the lesson as "Now you can"), and hints that escalate. `npm run effort` lists gaps in existing lessons; the audit is not done yet (roadmap/shared.md › Effort).
- Do not add rigid pedagogy rules. Clips only where useful (hook, expected result without code, explaining why).

## Teaching decisions

- PRIMM (code lessons only; maths uses Predict, Try, Worked example, Vary, Practise, Make, and science uses 5E on the same stages): Predict (lock in, compare after Run), Run, Investigate, Modify, Make. Investigate tools must follow the lesson insight. Several tasks per step show as sub-pills only when more than one.
- "Explain it to me" (`explainClip`, `teacher.yml` `explain`, `explainPicture`) opens from the "? - Expected results are clear and shown (BUILDING › 4): a picture (`expected:`, HTML) when static, an output-only clip when it moves, a short captioned clip to explain a spatial idea; never the code.
- Real-world content is a small complete example students Modify (the heading names the task). Make is an explicit task. Large projects belong to the teacher (For teachers panel).

## Playground runtime
- HTML playground: live preview (no Run); **Boxes** button or `?boxes=1` outlines every element with its tag name, coloured by depth (skips the browser-added `tbody`; rows get a thick outline, no label); `?zoom=` enlarges code and preview for clips. **Box model** button, `?boxmodel=1` or `?inspect=<selector>` (pinned): a layout-neutral overlay of margin, border, padding and content with sizes, for the CSS lessons (Boxes and Box model are never on together). `picture:` takes `inspect:` too. Pictures render in standards mode, like the preview. Every preview gets a `<base>` pointing at `_playground-html/media/` (course pictures from `media/html/`, so `src="trophy.svg"` works) and a click handler: web links open in a new tab, `#name` links scroll. Injected parts go before the student's code (after a `<!DOCTYPE>`). Sending a form shows a note ("Nothing was sent..."): the preview is sandboxed without forms, on purpose.
- DOM playground (`playground-dom/`): the preview's `<base>` is its `media/` folder, which holds the course pictures and the web libraries from `vendor/web/` (Bootstrap, Bulma, Pico, Tailwind's browser build, daisyUI, Vue, Preact with htm, Svelte), also copied into the HTML playground's `media/`; pages load them as files beside them (`<script src="vue.js">`), never from a CDN. Svelte components sit in `<textarea data-svelte hidden>`. The sandboxed preview has no storage, so the shim gives it a `localStorage` stand-in that the playground keeps per step (`wp-dom-store:<id>`; each Run is a new visit; `?store=0` starts empty); the HTML preview gets an in-memory one. Both playgrounds have a **Download** button (`playground-html/download.js`): `index.html`, wrapped in a whole page if needed, plus links for every file it uses from `media/`.
- `npm run check-html` walks every lesson of HTML & CSS, Bootstrap, the DOM course, Vue and Your site: regions render, pictures load, every check passes with its stored answer, every solution ticks its code check.
- The turtle playground is our own Skulpt bridge (`playground/skulpt-bridge.js`) plus a canvas renderer (`playground/canvas-turtle.js`), not Skulpt's turtle.
- Console mode (11 Oct, for `content/code/console/`): when a step's starter never mentions `turtle` (or `?console=1`), the turtle playground shows a console in place of the drawing; `input()` asks on an inline line (`.con-in`, aria-label Answer), time waiting for an answer does not count towards the run's time limit, output is capped at 40,000 characters, and Stop ends a waiting `input()`. Turtle starters never switch. Friendly hints for joining a number onto text and for `int()` on non-digits.
- Friendly errors (11 Oct): `tools/python-errors.mjs` (pure; copied into `_playground/` and `_playground-py/` by build-playground) turns Python's message into "Line N: the slip and the next move", never the task's answer. Skulpt says "bad input" for every syntax slip, so syntax errors are diagnosed from the student's code (quote, bracket, colon, `=` in a condition, indentation, missing brackets). The turtle playground shows the hint first, a **Show line N** button (switches to a module's tab if the error is there), then "Python says: …"; status "Error on line N". The Pyodide playground passes `{ turtle: false }`. `npm run check-python-errors` tests 26 slips against Skulpt and CPython messages; add a case there for each new rule.
- Events: `onscreenclick`, `onkey`, `ontimer`, `listen`, `textinput`, `numinput`. `mainloop()`/`done()` waits for events until Stop; with nothing registered it returns at once. Code checks and the Run-step compare box accept a Stopped run. Keys need the picture clicked first.
- `predict` check: a locked prediction is stored in `wp-predict`; the next Run step shows it beside the real result.
- MakeCode playground (`playground-makecode/`, `try: { playground: microbit | arcade }`): the real MakeCode editor in controller mode; our page stores the projects (per step, `wp-makecode-playground:<step>`) and reports `main.ts` (blocks compile to it) on the HTML playground's channel, quiet until the student changes something. Each step's editor loads on click ("Open the MakeCode editor"; Full screen and `?full=` open it too), because MakeCode focuses itself on load and lazy-loaded editors scrolled the page. Lessons whose extension is `wide` (robot) open it full screen, since MakeCode hides extension simulators in a narrow window. In full screen, any playground shows a task drawer (`.try-task`): the step's or open task's text, hints and code pictures (cloned from the page, refreshed when the task pill changes; Hide task folds it), then its code checks with ticks pinned at the bottom (`.try-checks`). Task checks normally listen only while their pill is open; MakeCode in full screen checks every task of the step, and opening a pill re-checks the editor's last report (`window.wpLast`). Follow the protocol rules in ROADMAP › MakeCode: embedding check (answer every re-sync with all projects, follow the new id after import, name in `pxt.json`). Code rules: `contains`, `inside: { "basic.forever": [...] }`, `count`, and `defs`/`calls`/`params` reading named MakeCode functions; students see the check text, not the rules. `language: makecode` lessons show code as blocks pictures (drawn by `render-pictures` through `render.html`, else live from MakeCode's renderer). What a program makes is drawn by MakeCode's own simulator at build time: `render-pictures` (section makecode-out) loads each `explainPicture` and `picture:` program into the playground in picture mode (`?sim=1`), starts the simulator and screenshots its biggest canvas or svg into `_pictures/makecode-out/<slug>/<key>.png`; the page shows it beside the blocks ("What it makes"). Test against the mock with `MAKECODE_EDITOR=/_mock/index.html` (a mock editor and simulator copied into `dist/_mock/`). This sandbox cannot reach makecode.com: test with the mock editor served at its address (Playwright route). `?tutorial=<path>` (a `/projects/...` docs path or `github:owner/repo/file`) opens a MakeCode tutorial with `startactivity` instead of a starter, follows its project and posts `{ wp: 'tutorial', event, step, total }` (not saved; ROADMAP › Parked). MakeCode lessons can name extensions in frontmatter (`extensions: [robot]`, keys and pinned versions in `MAKECODE_EXTENSIONS`): the lesson page passes them as `?pkg=name=version,...` to each playground (added to the project's `pxt.json` dependencies) and as `options.package` to the blocks renderer (page and build time).

## Gotchas
- Quote YAML captions that contain colons.
- HTML lessons: tags in Markdown text (lesson text, task bodies, hints, teacher Markdown fields) go in backticks (a bare `<h1>` becomes a real tag on the page, guide and slides; a bare `<style>` swallows the page's script); validate warns, and `check-html` fails if a lesson script did not run. Plain-text check and teacher fields are escaped by the generators (`pt` in `teach.mjs`).
- Display-only code regions (bug, compare, parsons) are not meant to run.
- Commit trailers: the `Co-Authored-By:` and `Claude-Session:` lines from the session reminder (they name the current model and session).
- Custom domain: tutorials.learningwaypoints.com is stuck on the suspended account. studio.learningwaypoints.com (Vercel, DNS and project settings on Matthew's side) is the working address.
